> v0.4 把「借 Chrome 开窗口」换成「应用自己的原生窗口」。本篇精读新文件 `monitor/desktop.py`，以及配套改动：`App.stop_now()`（`server.py`）和 `run.py` 的主线程安排。代码片段原样截取，行号是 v0.4.0 的真实行号。

## 本篇会遇到的新词

| 词 | 一句话解释 |
|---|---|
| 主线程 | 程序启动时的第一条执行线。macOS 规定窗口、菜单这些界面东西只能在主线程里创建和操作 |
| 事件循环（run loop） | 窗口程序的主线程一直在「等事件 → 处理事件」地转圈：鼠标点击、按键、系统发来的「请退出」都是事件 |
| WKWebView / WebView2 | 操作系统自带的「网页显示组件」：macOS 的叫 WKWebView（和 Safari 同一个引擎），Windows 的叫 WebView2（和 Edge 同一个引擎）。pywebview 把它们包装成 Python 能用的窗口 |
| 同步 / 异步 | 同步：做完才返回；异步：交给别的线程去做，自己马上返回 |
| 信号（signal） | 操作系统发给进程的通知，例如 SIGTERM「请结束」、SIGINT（Ctrl+C） |
| osascript | macOS 自带的命令，能运行 AppleScript 小脚本，这里用来弹系统通知 |

## 1. 为什么要改、改了什么

v0.1 为了「零第三方依赖、Windows 优先」，借用 Edge/Chrome 的 `--app` 模式开窗口：窗口是另一个程序（浏览器）的进程，本应用靠「看门狗」盯着它，窗口没了再退出。v0.4 改成和其他几个应用一样，用 pywebview 把系统自带的网页组件嵌进**本应用自己的窗口**：

| | v0.3（借 Chrome） | v0.4（原生窗口） |
|---|---|---|
| 进程 | 后台 + 一整套 Chrome 进程 | 一个应用进程（网页由系统 WebKit 辅助进程渲染） |
| 程序坞 | 显示 Chrome 图标 | 显示「舆情监控」 |
| 退出 | 窗口进程结束 → 看门狗发现 → 后台退出 | 关窗事件里当场收尾 |
| 内存（2026-10-22 实测） | 后台约 37 MiB + Chrome 多个进程 | 应用进程约 91 MiB |

## 3. 关键代码逐段讲解

### 3.1 run.py：主线程留给窗口

`run.py` 第 105–110 行：

```python
105      app.collector.start()
106  
107      # HTTP 服务放到子线程：主线程要留给原生窗口（macOS 规定窗口必须在主线程里创建）
108      server_thread = threading.Thread(target=httpd.serve_forever, kwargs={"poll_interval": 0.5}, name="http", daemon=True)
109      server_thread.start()
110  
```

v0.3 时主线程在跑 HTTP 服务（`httpd.serve_forever()`）。现在主线程要留给窗口（macOS 的规定），所以把 HTTP 服务挪进子线程 `server_thread`。`daemon=True` 表示「主线程结束时不用等它」。

`run.py` 第 128–141 行：

```python
128          cfg = app.store.settings()
129          if args.no_browser:
130              pass
131          elif cfg["browser"] == "auto" and desktop.run_window(app, url):
132              app.shutdown("应用窗口已关闭")  # 窗口已关：已经在退出流程里时这一句什么也不做
133          else:
134              app.browser_mode = browser.open(url, cfg["browser"], cfg["app_window"])
135          while server_thread.is_alive():  # 等退出流程把 HTTP 服务停掉；用短超时循环，Ctrl+C 才能及时响应
136              server_thread.join(0.5)
137      finally:
138          watchdog.stop_event.set()
139          browser.close()
140          httpd.server_close()
141          app.stop_now("程序结束")  # 已经在窗口关闭时收尾过的话，这里什么也不做
```

- **第 129–134 行**：设置是「自动」就先试原生窗口。`desktop.run_window()` 会一直阻塞到窗口关闭；返回 False（没装 pywebview、组件不可用）就走 `else`，用 v0.3 的 Edge/Chrome 窗口。这叫「优雅降级」：好的方式不行，退回能用的方式，而不是直接报错。
- **第 135–136 行**：用 0.5 秒一次的短等待循环等服务线程结束，而不是一直 `join()`。原因：Python 只在主线程「有空」时才处理 Ctrl+C 这类信号，一直卡在 `join()` 里信号会被耽误。
- **第 141 行**：最后再调用一次 `stop_now`。如果关窗时已经收尾过，这里什么也不做（见 3.3 节的「可重复调用」）。

### 3.2 开窗口和三项补丁

`monitor/desktop.py` 第 37–51 行：

```python
37  def run_window(app, url: str) -> bool:
38      """在主线程打开原生窗口并阻塞到窗口关闭。成功打开过返回 True；打不开返回 False（调用方改用浏览器）。"""
39      try:
40          import webview
41      except Exception as exc:  # noqa: BLE001
42          log.info("没有 pywebview（%s），改用 Edge/Chrome 窗口", exc)
43          return False
44      try:
45          webview.settings["ALLOW_DOWNLOADS"] = True
46          webview.settings["OPEN_EXTERNAL_LINKS_IN_BROWSER"] = True
47          window = webview.create_window(
48              f"{APP_NAME} v{__version__}", url, width=1440, height=900, min_size=(900, 600), text_select=True,
49          )
50          app.native_window = True
51          app.collector.notifier = notify
```

- **第 40 行在函数里面才 `import webview`**：没装 pywebview 的电脑（比如源码运行）导入失败也不会让整个程序起不来，只是返回 False 走后备方式。
- **第 45 行 `ALLOW_DOWNLOADS`**：嵌入式网页组件默认不处理下载，打开后「导出 CSV」「下载源码 zip」会弹出系统的「存储为」对话框。
- **第 46 行 `OPEN_EXTERNAL_LINKS_IN_BROWSER`**：带 `target="_blank"` 的链接（资讯原文、官方文档）交给系统默认浏览器打开。不这样做的话，应用窗口会整个跳到外部网站，回不来。
- **第 51 行**：把系统通知函数交给采集器。浏览器自带的网页通知功能（`Notification`）在嵌入式组件里不可用，所以改由后台直接弹系统通知。

### 3.3 关窗时同步收尾：这次最关键的改动

`monitor/desktop.py` 第 53–75 行：

```python
53          closing = threading.Event()
54  
55          def on_closing():
56              closing.set()  # 告诉 watch_quit：窗口已经在关了，不要再去关它
57              # closing 事件在主线程同步执行：红色关闭按钮、⌘Q、程序坞「退出」都会先经过这里，
58              # 返回后 macOS 可能直接结束进程，所以收尾要在这里做完（v0.4 实测：只挂 closed 时日志缺「已退出」）
59              log.info("应用窗口正在关闭")
60              app.stop_now("应用窗口已关闭")
61              return True
62  
63          window.events.closing += on_closing
64          window.events.closed += lambda *_: app.shutdown("应用窗口已关闭")
65  
66          def watch_quit():  # 页面上点「退出」或收到退出信号：关掉窗口，webview.start() 随之返回
67              app._stopping.wait()
68              if closing.is_set():
69                  return
70              try:
71                  window.destroy()
72              except Exception:  # noqa: BLE001
73                  pass
74  
75          threading.Thread(target=watch_quit, name="quit-watch", daemon=True).start()
```

**踩过的坑（2026-10-22 实测）**：第一版只挂了 `closed`（「已关闭」）事件，在里面调用异步的 `app.shutdown()`。给测试进程发「退出」信号（和程序坞右键「退出」是同一个信号）后，进程 1 秒就没了，但日志里**没有「已退出」这一行**：数据库没来得及正常关闭，采集线程也是被硬切断的。

**原因**：读了 pywebview 的源码（`webview/platforms/cocoa.py`）。macOS 收到「退出」时先问应用「能退出吗」（`applicationShouldTerminate_`），pywebview 在这一步同步调用每个窗口的 `closing` 事件；只要没人反对，系统就直接结束进程，**不会再回到 `webview.start()` 之后的 Python 代码**。

**修法**：
- **第 55–61 行**：把收尾挪到 `closing` 事件里。pywebview 创建 `closing` 事件时设了 `should_lock=True`，表示处理函数在主线程上**同步执行**，执行完才放行。这里调用同步的 `stop_now()`，当场停采集、停服务、关数据库，然后返回 True（同意关闭）。红色关闭按钮、⌘Q、程序坞「退出」三条路都会经过这里。
- **第 53、56、68 行**：`stop_now()` 会触发「正在退出」标志，唤醒 `watch_quit` 线程，它本来会去关窗口。但这时窗口本来就在关，再去关同一个窗口可能出错。所以用一个 `closing` 标志告诉它「不用你管了」。这是典型的「两个线程都想做同一件事」的竞态，用一个标志让其中一个让路。
- **第 66–73 行 `watch_quit`**：反方向的路径。页面右上角点「退出」时，后台先开始退出，这个线程看到标志后关掉窗口，`webview.start()` 随之返回，`run.py` 接着收尾。

修完后的实测结果（打包好的 .app）：程序坞「退出」1 秒内进程结束，端口释放，日志依次是「应用窗口正在关闭」「已退出（应用窗口已关闭）：采集已停、服务已停、数据库已关闭」。

`monitor/server.py` 第 79–91 行：

```python
79      def stop_now(self, reason="用户退出"):
80          """同步退出：走完 shutdown() 的步骤后，当场停 HTTP 服务、关数据库再返回。
81          给原生窗口用：macOS 上 ⌘Q / 程序坞「退出」时，系统在窗口的 closing 事件返回后就直接结束进程，
82          不会再回到 run.py 的收尾代码，所以收尾必须在这里同步做完。可以重复调用。"""
83          with self._final_lock:
84              if self._finalized:
85                  return
86              self._finalized = True
87          self.shutdown(reason)
88          if self.httpd:
89              self.httpd.shutdown()  # 等 serve_forever 的循环退出（最多约 0.5 秒）
90          self.store.close()
91          log.info("已退出（%s）：采集已停、服务已停、数据库已关闭", reason)
```

- **第 83–86 行「只做一次」**：用锁保护一个标志 `_finalized`。关窗时调用一次，`run.py` 收尾时又调用一次，第二次直接返回。这种「可以放心重复调用」的性质叫**幂等**，退出这类可能从多个方向同时触发的操作，都应该写成幂等的。
- **第 89 行 `httpd.shutdown()`**：让 HTTP 服务线程的循环停下来，并**等它真的停了**才返回，这就是「同步」。服务每 0.5 秒检查一次停止标志，所以最多等约 0.5 秒。
- **第 90 行**：关数据库。之后再有线程想写数据库会报错，所以必须在停采集之后。

### 3.4 系统通知：参数传递，不拼字符串

`monitor/desktop.py` 第 89–99 行：

```python
89  def notify(title: str, message: str) -> None:
90      """系统通知。macOS 用自带的 osascript（文字作为参数传入，不拼进脚本，避免引号出错）；其他系统暂不支持。"""
91      if sys.platform != "darwin":
92          return
93      script = "on run argv\ndisplay notification (item 2 of argv) with title (item 1 of argv)\nend run"
94      try:
95          subprocess.Popen(["osascript", "-e", script, title, message[:200]],
96                           stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
97      except OSError:
98          log.debug("系统通知不可用", exc_info=True)
99  
```

- **为什么不拼字符串**：最直接的写法是 `osascript -e 'display notification "<消息>"'`，把消息拼进脚本。但预警消息来自外部网站的新闻标题，可能带引号。一个引号就会把脚本截断出错，严格说还可能让人在标题里塞进脚本命令。所以这里脚本是固定的，消息作为**参数**单独传进去（`on run argv` 读取），无论内容是什么都只会被当成文字。测试 `test_notify_passes_text_as_arguments` 检查了这一点。这和数据库里用 `?` 占位、不拼 SQL 是同一个道理。
- 通知是通过「脚本编辑器」发出的，所以 macOS 第一次会以「脚本编辑器」的名义询问是否允许通知。

## 4. 错误处理与边界

| 情况 | 处理 |
|---|---|
| 没装 pywebview / 窗口组件不可用 | 退回 Edge/Chrome 窗口（v0.3 方式），看门狗照旧 |
| 被 `kill`（SIGTERM） | 信号处理函数走退出流程。窗口模式下 Python 要等事件循环交还控制权才能处理信号，实测延迟约 7 秒，但收尾完整 |
| 被强制结束（`kill -9`、活动监视器「强制退出」） | 窗口和后台是同一个进程，一起消失，不会遗留后台；数据库每次写入都已提交，不丢数据 |
| 窗口缩放、深浅色等界面偏好 | 存在 `数据目录/webview/` 里（网页的 localStorage）。从 v0.3 升级后要重新选一次缩放档位，因为旧的存在 Chrome 的配置目录里 |

## 5. 动手练习

2. **想一想**：如果 `on_closing` 返回 False 会怎样？（提示：pywebview 会取消关闭。可以用这一点做「有任务没完成时，关窗前先确认」。）
3. **让 Windows 也有系统通知**：在 `notify()` 里加 Windows 分支。查一查 PowerShell 怎么弹「Toast 通知」，注意同样用参数传文字，不要拼字符串。

## 读完你应该懂了什么

- macOS 规定窗口只能在主线程里，所以 HTTP 服务要让出主线程。
- 「关窗/⌘Q」时系统可能不给程序第二次机会，收尾必须在「关闭前」的同步事件里做完。
- 退出这类可能从多个方向触发的操作要写成幂等的；两个线程抢着做同一件事时，用标志让一个让路。
- 把外部内容交给脚本时，用参数传，不要拼字符串。
