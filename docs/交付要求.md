> 给 Claude 的指令：在本仓库开发或修改应用前，先读本文件。默认交付是 **macOS 应用**：由 GitHub Actions 在 macOS 机器上构建 `<项目名>.app` 并打成 `.dmg`，用户下载后拖进访达的「应用程序」。关闭最后一个窗口或退出应用时，停止本应用自用的后台。应用内的总入口统一叫「使用指南」，完整呈现本项目 `docs/` 里的全部文档和附件（也就是同步到 Obsidian 的那一份），包括软件框架、系统架构、源码与学习资料，并可用图片、图解和示例讲得更详细。页面同时显示真实的进程和内存状态，并提供整体界面缩放：**70%–120%，每 5% 一档**，**百分比选择和「−」「＋」按钮都要有**。每次修改程序，都在同一任务内同步更新代码、使用指南、`docs/` 和安装包。需要持续运行的后台，须在设计阶段向用户说明并明确约定。

## 适用范围

本文件适用于在本仓库开发、以 HTML/React 等网页界面呈现的本地应用。默认交付形态是可安装的 Mac `.app`，通过应用窗口显示界面。具体技术、数据来源和内部实现由各项目自己决定。这是一份**交付要求**，不规定统一的技术栈或开发流程。

用户明确选择纯网页、独立 HTML、Windows 或其他平台时，按当次选择交付；否则执行下面的 Mac 应用要求。

## 云端环境与 Codex 本地的区别

Claude 在云端的 Linux 容器里工作，每次会话都从 GitHub 重新克隆本仓库，碰不到用户的 Mac。原要求里依赖本机的部分按下表改做：

| 原要求（Codex 在 Mac 本地） | 云端做法 | 由谁完成 |
|---|---|---|
| 生成并安装 `/Applications/<项目名>.app` | GitHub Actions 在 macOS 机器上构建 `.app` 并打成 `.dmg`，Claude 给出下载链接 | Claude 构建；用户下载并拖进「应用程序」 |
| 写入 `Obsidian Vault/Codex/<项目名>/` | 写进仓库的 `<项目目录>/docs/`，目录结构和 Obsidian 项目文件夹一致 | Claude 写；用户同步到 Obsidian |
| 在 Mac 上实测双击打开、⌘Q、程序坞退出 | 能自动化的放进 CI 的 macOS 冒烟测试；界面在容器里用无头浏览器实测；其余列入「待用户在 Mac 上验收」 | 双方分工 |
| 最终回复给出项目根目录的本地链接 | 给出 GitHub 上的链接：分支或 PR、文件、构建产物或 Release 下载页 | Claude |
| YAML 写 `author: Codex` | 写 `author: Claude` | Claude |

## 仓库约定

- 每个应用占一个顶层目录（如 `quant-lab/`），里面放源码、`docs/`、`tests/`、`packaging/` 和 `README.md`。每个应用有自己的工作流 `.github/workflows/<项目目录>.yml`，用 `paths` 限定只在本项目有改动时才构建。AI 知识视频工坊放在仓库根目录，是早期的例外。
- 在以 `claude/` 开头的分支上开发并推送，推送后自动触发 CI 构建。
- 数据和用户设置放在 `~/Library/Application Support/<项目名>/`（Windows 放在 `%APPDATA%\<项目名>\`），不放进 `.app` 里，这样替换新版本时不会丢数据。

## 必须完成的四处交付

### 1. 可安装的 macOS 应用

- CI 产出 `<项目名>.dmg`（或 zip），解开就是 `<项目名>.app`。拖进「应用程序」后双击即可打开界面。日常使用不能要求用户开终端，也不能要求用户先装 Python 或 Node。只有源码、HTML、`.command` 启动脚本，不算完成交付。
- 默认构建 Apple Silicon 版。用户需要时再加 Intel 版或 Windows 版。
- 没有 Apple 签名和公证时，使用指南要写明首次打开的方法：右键选「打开」，或到「系统设置 → 隐私与安全性」里点「仍要打开」。用户提供开发者账号后再加签名。
- 写清应用名称、版本号、安装位置、启动和退出方式。界面上显示版本号，方便用户确认自己装的是哪一版。
- 依赖外部账号、数据服务、网络或特定目录时，写清准备方式和迁移条件，不能说成「任何 Mac 都免配置」。

**默认按需启停，避免应用结束后继续占用资源。** 应用负责启动和停止它自用的后台和工作进程，默认行为如下：

| 用户操作 | 默认要求 |
|---|---|
| 菜单「退出」、⌘Q、程序坞右键「退出」 | 退出应用，并停止本应用自用的后台、采集/计算任务和工作进程 |
| 点击红色关闭按钮，关闭最后一个窗口 | 同样退出应用并停止上述后台；有多个窗口时，关掉其中一个不等于退出 |
| 最小化、隐藏或切换到其他应用 | 应用与后台继续运行；使用指南要说明这种区别 |

正常退出时，先保存必要设置、结束任务、停止所属后台，并确认相应进程已经退出，然后才完成应用退出。清理临时 PID、端口等运行记录只是收尾动作，既不能代替停止后台，也不能删除用户数据或设置。崩溃或强制退出时可能跳过正常的退出回调，所以要有异常收尾机制，例如工作进程定时检查主进程是否还在，主进程不在了就自行退出；同时说明监测的对象和用途。独立的外部服务，以及与其他应用共享的进程，不在随本应用停止的范围内。

**关闭窗口或退出应用后仍要持续运行的后台，是单独约定的功能。** 开发前向用户说明它的目的、哪些操作之后仍会运行、资源影响以及如何彻底停止，并取得明确同意；用户已经明确提出要求的，不必重复确认。界面和使用指南都要写清当前状态和停止入口。

更新已有项目时，保持应用名称、数据目录和用户设置不变，并递增版本号。

### 2. 应用内「使用指南」与界面控制

应用内承载全部项目资料的总入口统一命名为 **「使用指南」**，放在主导航、菜单或其他明显位置。总入口下可以按主题分成多页，各页按内容命名，如系统架构、源码阅读、研究报告。这里要提供完整的项目资料，不能只放简短的操作帮助或一个跳转链接。

**应用内文档的覆盖范围不得少于 `docs/`。** 按 `docs/` 逐项建立文档与附件清单，每篇都要在应用内完整呈现，包括项目说明、需求与设计、使用指南、软件框架、系统架构、源码解读、数据口径、研究或实验报告、学习资料和维护记录等实际交付的内容。`docs/` 里已有的详细章节，不能在界面里只留摘要。历史资料要保留日期或版本，并和当前说明清楚区分。

图片、PDF、Excel、JSON、源码包等附件，在应用内也要有明确入口：适合阅读的提供预览，其余提供打开或下载原文件，并注明用途和版本。

界面里可以讲得比 `docs/` 更详细。软件框架、系统架构和源码学习部分，用架构图、调用链图、操作截图、图表、代码示例或交互演示来帮助理解，图片和示例必须对应实际版本。建议的阅读顺序是「软件用途与框架 → 系统架构 → 源码阅读 → 操作与结果」。文档随应用一起打包，离线也能阅读。

至少完整说明以下八项内容，并提供其中涉及的实际界面功能：

1. **怎样开始和结束**：安装和首次打开的方法、首次准备、需要登录或开启的外部服务；分别写清关闭最后一个窗口、菜单或程序坞「退出」、⌘Q、最小化时应用和后台的行为。
2. **怎样完成主要任务**：各页面的用途、最常用的操作顺序，筛选、刷新、导入、导出等按钮的效果，以及结果在哪里查看。
3. **数据从哪来、何时更新**：数据来源、统计口径与单位、缓存或历史快照、自动和手动更新的触发条件；缺失、零、失败、未披露要按实际含义区分。
4. **结果如何理解**：关键字段、图表和指标的读法、适用范围、已知限制，以及还没实现或还没验证的能力。
5. **出了问题怎么办**：最常见的依赖缺失、服务未启动、权限或网络失败、数据没更新时，应按什么路径检查。
6. **软件框架、系统架构与源码**：软件要解决什么问题、模块如何组织，窗口/页面、后台、数据和外部服务之间的关系；给出架构和调用链、主要手写文件和关键函数的职责、源码阅读路线、修改与重建方法，并提供完整手写源码的查看或下载入口。
7. **当前进程与内存**：在页面的运行状态区域，显示本次启动涉及的每个应用进程，包括职责或名称、当前 PID、实际内存占用和采样时间。标明口径和单位，例如常驻内存 RSS、MiB（1 MiB = 1024² 字节）。后台、窗口进程、应用自己启动的工作进程各有 PID 的，要逐个列出；应用外部的独立依赖单独列出，不计入本应用合计。同一进程里的线程共享 PID，不能把线程数说成进程数。没有独立后台时明确显示「无独立后台」；读不到时显示「暂不可用」，不能拿旧 PID 或估算值冒充当前状态。合计值如果是各进程 RSS 相加，要说明共享内存可能被重复计算。
8. **怎样缩放界面**：说明缩放控件的位置，如何选择具体百分比、如何用「−」「＋」逐档调整，以及如何恢复到 100%。

**界面缩放控件**应放在主界面容易找到的位置，优先放在顶部靠右，做成紧凑的一组。**两种操作必须同时提供：点击百分比控件选择具体档位，以及点击「−」「＋」逐档调节。** 窄屏时可以收进顶部菜单，但两种操作都要可用。

- 范围是 **70%–120%，每 5% 一档**，共 11 档：70%、75%、80%、85%、90%、95%、100%、105%、110%、115%、120%。
- 「−」每次减 5 个百分点，「＋」每次加 5 个百分点。到 70% 时禁用「−」，到 120% 时禁用「＋」。百分比控件和加减按钮显示同一个当前值。
- 默认 100%，另提供一键恢复。
- 缩放作用于整个应用界面，包括文字、按钮、表格、图表和文档。切换页面和重新打开应用后，保留用户的选择。
- 每一档下，关键操作都要能看到、能点击，不能出现文字被截断或控件重叠。

### 3. Obsidian 项目文档（仓库内 `<项目目录>/docs/`）

```text
<项目目录>/docs/
├── 00 项目阅读入口.md          # 项目是什么、怎么安装和打开、先读哪篇、当前状态
├── 01 使用指南.md              # 启停、操作、数据、导出、故障与限制
├── 02 软件框架与系统架构.md    # 软件组织、组件、调用链、数据位置
├── 03 源码阅读与重建指南.md    # 手写文件、关键函数、阅读路线、修改与重建
└── assets/                     # 图片、图解、附件
```

可以按项目规模合并或拆分，但上述内容和清楚的导航都要保留。

- 这份 Markdown 同时是应用内「使用指南」的来源：构建时打包进应用，保证两处内容一致。界面里额外的图解或交互内容可以另外增强。
- 链接一律用标准 Markdown 相对链接，例如 `[使用指南](<01 使用指南.md>)`，这样 GitHub 和 Obsidian 都能点开。不要用 `[[双链]]`，因为 GitHub 上不会显示成链接。
- 用户同步到 Obsidian 的方法（任选一种）：
  - 把本仓库 clone 到 vault 里（例如 `Obsidian Vault/Claude/`），之后用 `git pull` 或 Obsidian Git 插件更新；
  - 下载 `docs/` 后复制到 `Codex/<项目名>/`。
- 阅读入口要指向安装方法、应用内「使用指南」和其余笔记。源码目录、安装包、运行数据目录（`~/Library/Application Support/<项目名>/`）和文档目录不能混为一谈。
- 使用指南要让没打开应用的人也能读懂，并解释进程/内存状态的范围、单位和查看方式，以及缩放控件的位置和档位。
- 新建或主要由 Claude 撰写的文章，YAML 写 `author: Claude`；只修改别人已有的文章，写 `reviewed_by: Claude`。文件名已经作为标题显示时，正文不再重复同名的一级标题。
- 源码说明要标明实际覆盖范围，以及排除了哪些第三方或生成的文件。

### 4. 交付清单与交接

- 最终回复列出「主要交付（N 个）」，每一项都给出 GitHub 上能直接点开的链接：安装包下载、源码目录、`docs/` 阅读入口，有 PR 时附上 PR。同一内容的多个副本只算一项。
- 写清安装包、源码、HTML、数据快照各自能做什么、不能做什么。
- 构建产物（Artifacts）需要登录 GitHub 才能下载，默认保留 90 天。正式版本打 tag（`<项目目录>-v<版本>`），由 CI 发布到 Release 长期保存。

## 每次修改同步维护

**每次修改程序，都在同一任务、同一次推送里同步更新以下内容：** 代码、`docs/`（也就是应用内使用指南和 Obsidian 文档）、图解与截图、版本号，并由 CI 重新构建安装包。不能只改程序、只改一处文档，或者把同步留到下次。

应用内文档至少要完整覆盖 `docs/`，可以更丰富；两处对同一事实的表述必须一致。需要核对的内容包括：应用名称与版本、安装方法、启停行为、页面功能、软件框架与系统架构、源码职责、数据来源与更新、结果口径、进程/内存范围、缩放方式和限制。当前 PID 和内存值由应用在运行时读取，文档只写查看方法和口径。

## 交付前的验收

### Claude 在云端完成

- 单元测试和 CI 全部通过。CI 在 macOS 机器上构建出 `.app` 并做冒烟测试：能启动，主要接口可用；发出退出指令（如 `osascript -e 'quit app "<项目名>"'`）后，自用进程都已结束，端口不再监听。
- 在容器里用无头 Chromium（Playwright）打开界面，逐项检查：
  - 走通一条主要操作。
  - 「使用指南」对照 `docs/` 清单逐篇检查：内容完整，图片能显示，附件能打开或下载；窄窗口下入口仍然找得到。
  - 缩放：11 档逐个验证；百分比控件和「−」「＋」显示一致，每次加减 5；到上下限时相应按钮被禁用；切换页面和刷新后档位保留；恢复 100% 有效。在 70%、95%、100%、120% 四档截图，确认没有截断或重叠。
  - 进程/内存列表与 `ps` 抽样一致；工作进程增减时列表跟着更新，不保留已结束进程的旧数值。
- 对照代码和配置，核对文档里写的端口、路径、更新频率、导出、权限，以及已实现/未实现。
- 回复里附上关键截图，并分别列出「已验证」和「未验证」两部分。

### 待用户在 Mac 上验收

以下几项由 Claude 列成清单交给用户，不能代为声称已完成：

- 下载安装包，拖进「应用程序」，完成首次打开（包括系统安全提示）。
- 从「应用程序」双击打开，走通一条主要操作。
- 分别试一次关闭最后一个窗口、⌘Q、程序坞「退出」，然后在「活动监视器」里确认本应用自用的进程都已结束。
- 页面显示的进程/内存数值与「活动监视器」大致一致。
- 在 Obsidian 打开「00 项目阅读入口」，确认各链接都能点通。

CI 通过、容器里截图正常，都不等于 Mac 上的验收已经通过。还没做的项一律写「待验收」或「待完成」，不能把预览、只读检查或旧版本测试说成本次交付已验收。
